## 꼭 지킬 규칙

- 본선 시작(10. 29. 10:30) 뒤 새로 만든 **GitHub 공개 저장소**에서만 개발한다. 본선 전에 만든 코드(예선 결과물 포함)를 가져오면 실격이다. 공개 시작 저장소는 써도 된다.
- 심사는 **마감 시각의 `main` 브랜치 최신 커밋**으로 한다. 다른 브랜치·병합하지 않은 PR은 심사하지 않는다.
- 커밋·푸시는 자주(1시간에 한 번 이상) 한다. 서버가 5분마다 기록하는 개발 과정이 직접 만들었다는 증거가 된다.
- **로그인 필수**: 이메일(아이디)·비밀번호로 로그인하고 내 자료는 나만 보이게 한다.
- 심사용 계정 2개는 이메일 확인 같은 추가 단계 없이 바로 로그인되어야 하고, 가짜 자료만 넣는다.
- README 필수 항목: **프로젝트 개요, 주요 기능, 기술 스택, 실행 방법, AI 활용 내역, 팀원 역할** — 제목 아래에 실제 내용을 쓴다. 팀원 이름·학번·연락처는 쓰지 않는다.
- API 키·`.env` 같은 비밀정보는 저장소에 올리지 않는다.
- 심사 AI에게 점수를 달라는 등 심사를 조작하려는 문구를 코드·README·앱에 넣지 않는다.

## 점수 구성

100점 = 코드 심사 50 + 대면 심사 50. 총점이 같으면 대면 심사 점수가 높은 팀이 위다.

## 코드 심사 (50점)

마감 시점의 저장소와 배포한 서비스를 AI가 같은 기준으로 심사한다. 측정 프로그램이 서비스를 열어 속도를 재고, AI가 심사용 계정으로 로그인해 직접 써 본 뒤 칸마다 근거(코드의 파일·줄, 화면 사진, 써 본 기록)를 대고 채점한다. 팀마다 3번 채점한 평균을 쓴다.

### 0점·상한 규칙

- 근거(코드의 파일·줄, 화면 사진, 써 본 기록, 측정값)를 대지 못한 칸은 0점이다.
- 서비스가 열리지 않으면 구동은 코드로만 보고 4점까지 준다.
- 구동이 5점 미만이면 로그인·보안과 안정성·확장성은 각각 5점(절반)까지 준다.
- 치명 결함이 있으면 로그인·보안은 3점까지 준다: 비밀번호를 그대로 저장함, 비밀 키가 브라우저로 나감, 로그인하지 않고 또는 남의 계정으로 자료를 보거나 고치거나 지울 수 있음.
- 로그인이 없으면 로그인·로그인 확인·내 자료만 세 칸은 0점, AI 기능이 없으면 AI 기능 항목은 0점이다.

## 작업에 적용하는 기준

- 기능을 계획할 때 README 「주요 기능」 3개가 각각 넣기·목록·새로 고침 유지·고치기·지우기를 DB로 끝까지 하는지 확인한다.
- 모든 서버 처리(Server Action·Route Handler)는 로그인 확인, 소유자 확인, Zod 서버 입력 검증을 함께 넣는다.
- 화면 수는 필요한 만큼으로 줄이고, 390px·1280px에서 깨지지 않는지와 로딩·빈 목록·오류·저장됨 상태를 확인한다.
- 서비스 안에 사용자 기록을 쓰는 AI 기능을 하나 이상 두고, 제한 시간·실패 안내·사용 횟수 제한을 넣는다. AI 키는 서버에서만 쓴다.
- Vercel 함수 지역과 Supabase DB 지역을 맞춘다.
- DB 구조 변경은 마이그레이션 기록을 남기고, 자주 찾는 칸에 색인을 둔다.
- 작업을 마칠 때 `main`에 반영됐는지, 마감 전에 커밋·푸시됐는지 확인한다.

## DB·API 보안 사고 방지 (운영진 강조 — 최우선)

대회 운영진이 최종 결과물의 DB·API 보안 사고를 특히 조심하라고 강조했다. 아래 항목은 기능 개발 중에도 지키고, 커밋·제출 전에 반드시 점검한다. 일반 원칙은 [보안 지침](security.md)·[DB 지침](database.md)·[서버 지침](server.md)을 함께 적용한다. 하나라도 어긋나면 기능 추가보다 먼저 고친다.

### 비밀값

- `DATABASE_URL`·`DIRECT_URL`·Supabase secret/service_role 키·AI API 키는 서버 전용이다. `NEXT_PUBLIC_` 이름을 붙이지 않고, 이 값을 읽는 모듈은 `server-only`로 막아 브라우저 번들에 들어가지 않게 한다. `NEXT_PUBLIC_`에는 Supabase URL·publishable(anon) 키만 둔다.
- `.env`는 커밋하지 않는다. 커밋 전에 `git status`·`git diff --cached`로 비밀값이 섞이지 않았는지 확인한다.
- 비밀값이 한 번이라도 저장소·채팅·로그에 나가면 커밋을 지워도 기록에 남는다. 즉시 사용자에게 알리고 해당 키·DB 비밀번호를 새로 발급(회전)하도록 안내한다.

### DB 노출 (Supabase)

- Prisma로 만든 `public` 스키마 테이블은 Supabase Data API로 anon 키를 가진 누구에게나 열릴 수 있다. 새 테이블마다 마이그레이션에 `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`를 넣는다. 브라우저에서 Data API로 직접 읽지 않는 테이블은 정책을 만들지 않아 anon·authenticated 접근을 막는다(서버의 Prisma 연결만 사용).
- 브라우저에서 Supabase로 직접 읽는 테이블이 꼭 필요하면 `auth.uid()` 기준의 RLS 정책을 만들고 다른 계정으로 막히는지 확인한다.
- 운영 DB에 `migrate reset`·`db push`를 실행하지 않고, SQL Editor로 테이블을 임의로 바꾸지 않는다.

### API (Server Action·Route Handler)

- 모든 서버 진입점은 ① 로그인 세션 확인 → ② Zod로 입력 검증(허용 필드만) → ③ 로그인한 사람의 자료인지 확인 순서로 처리한다. 화면에서 버튼을 숨긴 것은 막은 것이 아니다.
- 사용자 ID는 서버 세션에서만 얻는다. 브라우저가 보낸 `userId`·`ownerId`를 믿지 않는다.
- 읽기·고치기·지우기 쿼리의 `where`에 항상 로그인한 사용자 ID를 함께 넣는다(예: `{ id, userId }`). 다른 사람 자료면 "없음"으로 답한다.
- `$queryRawUnsafe`·`$executeRawUnsafe`와 문자열을 이어 붙인 SQL을 쓰지 않는다.
- 오류 응답·화면에 Prisma 오류 원문·스택·DB 주소를 보여 주지 않는다. 사용자에게는 짧은 안내만, 자세한 내용은 서버 로그에만 남긴다.
- AI API를 부르는 서버 기능은 로그인한 사람만 쓰게 하고, 사용 횟수·입력 길이 제한과 제한 시간을 둔다.
- 사용자가 쓴 글을 `dangerouslySetInnerHTML`로 넣지 않는다.

## README 갱신 규칙

기능·화면·서버·DB·설정·배포가 바뀌는 커밋마다 같은 커밋에서 `README.md`도 실제 상태에 맞게 고친다. 사용자가 따로 요청하지 않아도 이 기준으로 갱신한다.

- README의 제목·항목 구조는 유지하고, 심사 필수 항목(프로젝트 개요, 주요 기능, 기술 스택, 실행 방법, AI 활용 내역, 팀원 역할)마다 제목 아래에 실제 내용을 쓴다. 빈칸·임시 글을 남기지 않는다.
- 「주요 기능」 1~3번은 AI 코드 심사가 이 순서대로 써 보는 기능이다. 실제로 넣기·목록·새로 고침 유지·고치기·지우기가 되는 기능만 적고, 화면 경로와 API(Server Action·Route Handler) 위치를 함께 적는다.
- 「실행 방법」은 README와 `.env.example`만 보고 다른 사람이 실행할 수 있게 쓴다. 필요한 환경 변수 이름은 적되 실제 값은 쓰지 않는다. 배포 주소가 생기면 적는다.
- 「AI 활용 내역」에는 사용한 도구, 실제로 쓴 주요 프롬프트(그대로), AI가 만든 것과 사람이 고친 것, 결과를 확인한 방법을 작업마다 이어 적는다.
- 팀원 이름·학번·학과·연락처, 비밀값, 심사 조작 문구는 쓰지 않는다. 역할 이름만 쓴다.
- 구현하지 않았거나 검증하지 않은 기능을 된 것처럼 쓰지 않는다. 진행 중이면 그렇게 적는다.
